# Xyra CCM — Custom OData Service Integration Specification

**Audience**: your SAP Basis/ABAP development team.
**Purpose**: build one small, read-only custom OData V2 service in your S/4HANA
system so Xyra's Rule Engine can read the real values it needs to evaluate your
security/compliance controls.

This document defines the *only* piece of custom development required to connect
Xyra to your real system. Everything else Xyra needs (connectivity/credential
verification) already works against standard SAP endpoints with zero custom
development — see Section 8.

---

## 1. Purpose

Xyra's Rule Engine continuously monitors security and configuration baseline
values inside your SAP system as part of automated compliance controls — for
example, whether `SAP*`'s password has been changed from its default, whether
`DDIC` is locked, or what a client-level decimal-notation setting is. These
values live in your user master and user-parameter data and are not exposed by
any single standard SAP Business API in a form Xyra can query generically across
arbitrary object/parameter combinations defined by your own control catalog.

This document specifies a small, read-only Gateway service (`ZXYRA_CCM_SRV`) your
team implements once. From that point forward, Xyra connects to it using
standard OData V2 — the same way it would connect to any other Gateway service.
No further code changes are needed on Xyra's side for this integration, ever,
regardless of how your control catalog grows.

---

## 2. Service definition

| | |
|---|---|
| Service (external) name | `ZXYRA_CCM_SRV` |
| ICF path | `/sap/opu/odata/sap/ZXYRA_CCM_SRV/` |
| Protocol | OData V2, JSON (`$format=json` or `Accept: application/json`) |
| HTTP method | **GET only** — this is a strictly read-only service. No POST/PUT/DELETE/MERGE, and therefore **no CSRF token fetch/handling is required** by Xyra as a client. |
| Entity type | `ObjectParameter` |
| Entity set | `ObjectParameterSet` |
| Key | Composite: `(ObjectName, ParameterType, ParameterId)` |

> **Confirm the actual ICF path after activation.** `/sap/opu/odata/sap/
> {ServiceName}/` is SAP Gateway's standard default registration path when a
> service is activated via SEGW or `/IWFND/MAINT_SERVICE` — but the external
> namespace segment is technically configurable at registration time. Please
> confirm the activated path in SICF once you register the service, and let us
> know if it differs from the default above. This requires **no code change on
> our side** — the base URL is a plain configuration field on our end, not
> hardcoded.

### Properties

| Property | Recommended ABAP type | Notes |
|---|---|---|
| `ObjectName` | `CHAR(50)` or `STRING` | e.g. `SAP*`, `DDIC`, `SAPCPIC` — mostly standard SAP default/service account names |
| `ParameterType` | `CHAR(20)` | Exactly one of: `GENERAL`, `SETGET`, `DEFAULT` |
| `ParameterId` | `CHAR(100)` or `STRING` | e.g. `Password Changed`, `BUK`, `Decimal Notation` |
| `ParameterValue` | `STRING` | Always returned as text; Xyra compares it as a string or number depending on the rule's operator |

## 3. Request/response contract

### `$filter` — the only shape you need to support

Xyra will only ever send a `$filter` combining exactly 3 `eq` clauses joined by
`and`, in this fixed order:

```
ObjectName eq '<value>' and ParameterType eq '<value>' and ParameterId eq '<value>'
```

No ranges, no `or`, no `substringof`/other functions, no nested groups. This is
the single simplest `$filter` expression shape in the OData V2 specification.

**Literal escaping**: a single quote (`'`) embedded inside a filter value is
escaped by doubling it (`'` → `''`) — this is standard OData V2 string-literal
escaping, applied by Xyra when it builds the request. Your filter-parsing code
(generated by SEGW, or your own if hand-rolled) should already handle this
transparently if you're using the standard Gateway filter-handling framework.

### Worked example — request

```
GET /sap/opu/odata/sap/ZXYRA_CCM_SRV/ObjectParameterSet?sap-client=100&$filter=ObjectName eq 'SAP*' and ParameterType eq 'GENERAL' and ParameterId eq 'Password Changed'&$format=json
Authorization: Basic <base64 of service-user:password>
```

### Worked example — response (200)

```json
{
  "d": {
    "results": [
      {
        "__metadata": { "type": "ZXYRA_CCM_SRV.ObjectParameter" },
        "ObjectName": "SAP*",
        "ParameterType": "GENERAL",
        "ParameterId": "Password Changed",
        "ParameterValue": "Yes"
      }
    ]
  }
}
```

`__metadata` and any other SEGW/RAP-generated boilerplate fields are fine and
expected — Xyra only reads `d.results[0].ParameterValue` and ignores everything
else. You do not need to suppress or customize standard framework output.

### Worked example — no match

```
GET .../ObjectParameterSet?sap-client=100&$filter=ObjectName eq 'SAP*' and ParameterType eq 'GENERAL' and ParameterId eq 'Nonexistent'&$format=json
```
```json
{ "d": { "results": [] } }
```
**HTTP 200**, not 404. See Section 6 — this distinction matters functionally.

## 4. Where to source each parameter type

The table/BAPI names below are standard, long-stable SAP user-administration
objects. Verify field-level specifics against your own system's release/support
package before final implementation — exact field names can shift slightly
across NetWeaver releases, and anything marked "verify" below is flagged
precisely because we have not validated it against a live system.

- **`GENERAL`** (examples: `Password Changed`, `User Type`, `Locked`,
  `Failed Logins`, `Roles Assigned`, `Security Policy`, `SAP_ALL`): these
  conceptually map to user-master data — table `USR02` (logon data: lock
  status, password-change date/flag, user type), `AGR_USERS` (role/profile
  assignments), and the standard RFC-enabled BAPI `BAPI_USER_GET_DETAIL`, which
  aggregates most of this without direct table access (generally preferable to
  raw table reads, both for correct authorization checks and forward
  compatibility across releases).

  **Verify with your team**: the exact mapping from a human-readable
  `ParameterId` like `"Roles Assigned"` or `"Security Policy"` to a specific
  BAPI return-structure field or table column is a business-logic decision this
  spec deliberately does not prescribe — your Basis/security team defines that
  mapping once, based on which specific baseline checks your organization
  actually runs. This is genuinely implementation-specific, not something a
  generic spec can assert as fact.

- **`SETGET` / `DEFAULT`** (examples: `BUK`, `WRK`, `Decimal Notation`,
  `Time Zone`): these map to the classic SAP user-parameter-ID ("SET/GET
  parameter") mechanism. Table `USR05` is the long-standing classic source for
  parameter ID/value pairs per user.

  **Lower confidence, verify with your team**: we are confident `USR05` and the
  SET/GET parameter concept are real and correctly named. We have *not*
  independently verified an exact function-module signature (a commonly
  referenced candidate is `SUSR_USER_PARAMETERS_GET_ALL`, but there are
  multiple candidates across releases, including via `BAPI_USER_GET_DETAIL`'s
  own parameter return table) against a live system — treat this as "the kind
  of API to look for," not a guaranteed-exact name, and confirm what's actually
  available on your release.

- **General note**: since `ObjectName` here is mostly SAP standard/default
  service accounts (`SAP*`, `DDIC`, `SAPCPIC`, `TMSADM`, etc.) rather than
  arbitrary end-user IDs, many `GENERAL` checks are really "default account
  hardening" checks — a domain SAP's own standard security reports (e.g. the
  `RSUSR003`-family checks for default-password status) already partially
  cover. Your team may find it faster to reuse logic/data those standard
  reports already compute rather than re-deriving everything from raw BAPI
  calls — an implementation choice, not part of this contract.

## 5. Auth & transport

- **HTTP Basic Authentication**, one dedicated read-only ABAP service user.
  Recommend minimal authorizations scoped only to this service (`S_RFC`/
  `S_SERVICE` as appropriate) — do **not** grant `SAP_ALL` to this account,
  despite the irony of it being the account that checks for `SAP_ALL` elsewhere.
- **HTTPS required** in any non-local environment. Basic Auth over plaintext
  HTTP is acceptable only for local development/testing, never production.
- `sap-client` is passed as a **URL query parameter** on every request (the
  standard way to select client on Gateway OData calls, not session/cookie-based
  client selection).
- **Future hardening, not required now**: OAuth2 or X.509 client-certificate
  auth as a later upgrade once your landscape supports it.

---

## 6. Empty-result vs. error semantics

- **Empty `results` array + HTTP 200** = "this ObjectName/ParameterType/
  ParameterId combination has no recorded value." This is a normal, expected
  outcome, not an error. Xyra's rule engine has `EXISTS`/`NOT_EXISTS` operators
  whose entire purpose is to test for exactly this state — treating "not found"
  as an HTTP error would make those operators meaningless.
- **HTTP 4xx/5xx** is reserved for genuine failures: service not activated,
  malformed request, backend/database error, authentication failure (401),
  authorization failure (403).

## 7. Verification checklist

Run these 5 requests against your implementation once built:

1. `GET .../ObjectParameterSet?sap-client={client}&$filter=ObjectName eq 'DDIC' and ParameterType eq 'GENERAL' and ParameterId eq 'Password Changed'&$format=json` with valid Basic Auth → **200**, one row.
2. Same request with a deliberately nonexistent `ParameterId` → **200**, `results: []`.
3. Same request with wrong credentials → **401**.
4. Same request with a wrong/missing `sap-client` → any **4xx** (the exact code is your choice — Xyra treats any non-2xx as "value not retrievable" and fails the affected rule closed, per its documented fail-closed behavior).
5. A `ParameterId` value containing a literal apostrophe (e.g. a hypothetical `"Manager's Approval"`) round-trips correctly when escaped as `''` per standard OData V2 literal escaping.

Xyra maintains a local reference implementation (`xyra-s4`, a lightweight
Node.js stand-in used for our own internal testing) that answers these exact
same requests in the exact same shape — if useful, we can share it so your team
can compare responses directly during development.

## 8. What does NOT need custom development

Xyra's Configuration page's "Test Connection" feature (reachability + credential
validation) already works against **any standard SAP Gateway-enabled S/4HANA
system with zero custom ABAP development**, using two endpoints that are already
standard on any such system:

- `GET /sap/public/ping` — standard, unauthenticated ICM reachability check.
- `GET /sap/opu/odata/iwfnd/catalogservice;v=2/ServiceCollection` — the standard
  SAP Gateway service catalog, which requires valid Basic Auth to return data.

Only the `ZXYRA_CCM_SRV` service described in this document needs to be built by
your team. Everything else in this document is either already present on your
system or explained purely for context.
